# dav1d optimisation baseline — 2026-06-11

Baseline commit: `6d681d5` (master) + measurement harness.
Build: meson `release` (-O3), gcc 13.3, x86-64 (Xeon Ice Lake-class,
AVX2 + AVX-512), nasm 2.16, full asm enabled, debug symbols on.
Environment: 4-core shared container, Linux 6.18; `perf` unavailable, so
deterministic counters come from valgrind (cachegrind/callgrind).

## Correctness gate at baseline

- libaom conformance vectors (22, per-frame MD5 vs libaom ground truth):
  **PASS** on full-SIMD and pure-C (`--cpumask 0`) paths.
- 12-clip corpus: SIMD and pure-C decodes bit-identical; reference MD5s
  recorded in `data/corpus/refs.json`.

- `motion-720p` (dense residuals, 18 Mbps) is as slow per pixel as 1080p
  film content: coefficient decoding dominates.

## Hotspots by content class (callgrind, 30 frames, 1 thread)

### motion-720p-8bit (dense residuals, 160M instr/frame — heaviest per pixel)

Entropy decode is ~64% of all instructions:
`msac_decode_symbol_adapt4_sse2` 23.1%, `decode_coefs` 15.4% (+10.3%
constprop +1.9% intops), `msac_decode_hi_tok_sse2` 5.3%,
`msac_decode_bool_adapt` 3.6%, `msac_decode_bool_equi` 2.5%,
`msac_decode_symbol_adapt8` 1.6%. Then `decode_b` 3.9%,
`cdef_filter_8x8_avx2` 3.9%, refmvs C 2.7%, `recon_b_inter` 2.6%,
palette (`read_pal_indices` + `order_palette`) ~2.6% inclusive.

### detail-1080p-8bit (film-like, 59M instr/frame)

`decode_coefs` 18.7%, msac asm ~24%, `prep_8tap_regular_avx2` 8.9%,
CDEF asm ~12.5%, `cdef_brow` C glue 3.9%, refmvs C ~7.4%, `decode_b` 3.6%.

### grain-1080p-8bit (film grain synthesis, 44M instr/frame)

msac asm ~25%, `decode_coefs` ~18.6% total; film grain asm
(`fgy_32x32xn` 6.2% + `fguv_32x32xn_i420` 5.5%) = 11.7%;
`prep_8tap` 5.0%; CDEF ~5.4%; refmvs C 4.4%; `load_tmvs_sse4` 3.4%.
Film grain adds ~12% instructions and (see counters) significantly more
cache misses: the grain plane copy + blend touches every output pixel
again (947k vs ~542k L1d misses/frame at 1080p10 vs detail 8-bit's 821k
at 10-bit).

### smooth-1080p-10bit (gradients, intra-heavy, 16M instr/frame)

**`dav1d_cdef_brow_16bpc` C glue is #1 at 10.5%** — more than any single
CDEF filter kernel (4x4 filter 7.6+4.4%, dir 6.7%, 8x8 filter ~7.2%
combined): per-8x8-block bookkeeping, top/bot pointer re-selection and
2x8 pixel backups. `load_tmvs_sse4` 6.0%, `prepare_intra_edges_16bpc`
3.5% (left-column strided gather is its hot loop),
`recon_b_intra_16bpc` 3.3%, wiener 3.7%, memcpy 2.6%.

### anim-720p-8bit (graphics, 18M instr/frame)

Same shape as detail: msac ~25%, `decode_coefs` ~21.7%, `prep_8tap` 4.9%,
`load_tmvs` 4.0%, `decode_b` 3.4%, refmvs C ~5.9%, CDEF ~6%.

## Conclusions → candidate patches

1. **Entropy decode (decode_coefs + msac asm, 40–64% everywhere)** is the
   biggest consumer but is serial (bitstream-dependent), already
   hand-tuned C + SSE2 asm with packed-token tricks; no safe headroom
   found at C level. Not attempted.
2. **CDEF apply C glue (1.9–10.5%)** recomputes its top/bottom neighbour
   pointers per 8x8 block per plane through a branchy goto chain, although
   the selection only depends on the sbrow and plane. → patch 1:
   hoist to per-row base pointers (also removes two gotos; −25 lines).
   Risk: low (pure loop-invariant motion, bit-exact by construction).
3. **refmvs C path (2.7–7.4%)**: spec-defined candidate scan with
   dedupe; the inner loops are already minimal; SIMD exists for
   load/save_tmvs + splat. Possible future target (e.g. SIMD
   `add_temporal_candidate` batch projection), higher risk.
4. **Film grain (11.7% on grain clips + extra memory traffic)**: asm
   kernels already AVX2; the extra full-frame copy for ungrained planes
   is inherent to the API (ungrained frame is the reference). No small
   patch available.
5. **Palette (~2.6% on screen-like content)**: wavefront entropy decode,
   ~61 instr/pixel including msac — real work, not waste.
6. **Thread scheduling**: at <3 ms/frame (screen clip) 4-thread decode is
   *slower* than 1-thread (338 vs 402 fps) — synchronisation overhead
   exceeds the win on trivially cheap streams. Measured precisely:
   4-thread decode of the screen clip executes +12.7% more instructions
   for identical output (~1.1M instr/frame of task/atomics overhead,
   diffuse across the scheduler, not one fixable function). Structural;
   documented, not attempted.
7. **`load_tmvs` is a fixed O(frame area) cost**: 85.45M instructions per
   60 frames of 1080p (~44 instr per 8x8 block) regardless of content
   complexity or thread count — 16.7% of the cheap screen clip, 6% of
   smooth, ~3-4% elsewhere. It is spec-mandated temporal MV projection
   and already SSE4 asm; a lazy/per-superblock variant would be a larger
   structural change.

## Measurement caveats discovered

- valgrind 3.22 masks AVX-512 from CPUID, so cachegrind/callgrind runs
  measure the **AVX2** kernels while wall-clock runs on this host use
  **AVX-512ICL** kernels where available. Counter deltas in DSP asm
  therefore do not always translate 1:1 to wall-clock on this host; C
  glue deltas do.
- msac entropy asm (SSE2) is always active on x86-64 regardless of
  `--cpumask 0` (SSE2 is baseline), so "pure-C path" measurements still
  use asm for symbol decoding.

## Patch validation: cdef_apply pointer hoisting

Beyond the conformance + corpus MD5 gate, the patch's special branches
were explicitly covered:

- a frame super-resolution stream (the `resize` branch; encoded with
  aomenc, now an optional 13th corpus clip) decodes bit-identically to
  the pre-patch build at 1/4 threads on both SIMD and pure-C paths;
- monochrome (the I400 chroma-skip guard) covered by the conformance set;
- multi-thread (`have_tt`) sbrow-start/end branches covered at 4 threads;
- ASan+UBSan build (asm disabled, so the patched C runs everywhere):
  clean over all conformance vectors, a corpus subset, and the
  super-resolution stream.

Two independent wall-clock comparison runs disagree in sign per clip and
swing ±5% run-to-run in this container, confirming the deterministic
counters as the only trustworthy small-delta signal here. The patch is
kept on the strength of the instruction-count reduction plus the code
simplification, not a wall-clock claim.

## Patch series 2: refmvs candidate helper inlining

Profile data showed gcc 13 leaves four small, hot candidate helpers in
refmvs.c out of line at -O3 (`add_temporal_candidate` ~84 instr/call at
~9k calls/frame, `add_spatial_candidate` ~22 instr/call at ~7k
calls/frame, plus the two extended-candidate helpers), paying call/spill
overhead comparable to the bodies and preventing loop-invariant hoisting
of `rf->pocdiff[]` / MV-precision flags. Three one-line ALWAYS_INLINE
annotations fix this. Combined effect (cachegrind, 30 frames/clip):

| clip | instr/frame |
| --- | --- |
| screen-1080p | −2.59% |
| lowbr-480p | −1.56% |
| anim-480p | −1.63% |
| anim-720p | −0.96% |
| noisy-720p | −0.79% |
| detail/grain 8&10-bit | −0.62…−0.76% |
| motion-720p | −0.71% |
| uhd-2160p | −0.31% |
| smooth-1080p | −0.29% |
| superres-720p | −0.18% (vs. its own baseline after patch 2a) |

No clip regresses; data cache misses neutral everywhere; total code
size +4.4 KB of .text (+0.25%). Wall-clock deltas are inside this
container's noise, as expected for wins of this size.

## Patch series 3: scan and parse helper inlining

The same call-count mining on fresh profiles found four more small, hot
static helpers left out of line by gcc 13 at -O3: `scan_row`/`scan_col`
(~16k calls/frame, ~54 instr/call) and `read_mv_component_diff` /
`read_vartx_tree` in decode.c. Measured separately (cachegrind, 30
frames/clip): scan_row/col −0.08…−1.02% instructions/frame, decode.c
pair −0.01…−0.18%, all 13 clips improving in both, cache misses
neutral, +2.9 KB .text combined.

Functions examined and *not* changed: `mc` (its 135 instr/call is
genuine dispatch work, and inlining would bloat both recon paths),
`dav1d_prepare_intra_edges` (cross-TU, would need LTO not annotations),
`memset_w1/w2` (reached via the `dav1d_memset_pow2[]` function-pointer
table, where the indirect call costs more than the 1–2 byte store it
performs — ~830k calls/30 frames on dense content; replacing the table
with an inlinable switch is a possible future patch but touches the
case_set macro family used across decode.c).

## Cumulative result vs session baseline

Instructions/frame (cachegrind, deterministic): **−0.96% to −3.42%
across all 12 baseline clips** (screen −3.42%, anim-480p −2.84%,
lowbr −2.54%, others −1…−1.8%), data cache misses ≤ +0.19%
(noise-scale), code size +7.3 KB of .text (+0.4%).

A final wall-clock run showed +18…+72% fps vs the morning baseline —
which is impossible from a ~1–3% instruction reduction and instead
demonstrates that **host load in this shared container varies by tens of
percent across hours**: cross-session wall-clock comparisons are
meaningless here. Only back-to-back A/B wall-clock runs (which showed
±5% noise) and deterministic counters are valid in this environment;
wall-clock claims for these patches should be made on quiet bare-metal
hardware.

## Real-content validation

Four real-content clips were added to the corpus from raw camera/screen
sources in the public aom-test-data bucket (crowd_run 360p 10-bit,
niklas 720p, real 1080p screen capture, rush_hour CIF), encoded locally
with SVT-AV1 like the synthetic clips. The landed patch series measures
**−1.54% to −3.08% instructions/frame on real content** (vs −0.96…−3.42%
on synthetic), bit-exact against a clean master build on every clip.
The standard industry clips (Chimera, Summer Nature, as used by the
Phoronix `pts/dav1d` profile) are on hosts this environment cannot
reach; on an unrestricted machine they would be the natural next
addition.

## Negative result: memset_pow2 table → inline switch (rejected)

Converting the `dav1d_memset_pow2[]` function-pointer table (six
single-store bodies behind an indirect call, ~830k calls/30 frames on
dense content) into an inlinable switch reduced instructions on all 13
clips (−0.05…−0.44%) — but cost +21.5 KB of .text (+1.2%) and
**+3.5…+10.6% L1i misses** on 12 of 13 clips. On the small-I-cache
low-power cores this project targets, that trade is wrong; gcc's refusal
to inline 32 sites was defensible. Rejected and reverted; a future
variant could convert only the 2–3 hottest sites, but the projected win
(~0.1%) does not justify a split API.

## AVX-512 sizing (interleaved same-session A/B, threads=1)

avx512icl vs avx2 kernels on this Ice Lake-class Xeon: +2.1% (detail
1080p 8-bit), +1.2% (detail 10-bit), +2.3% (real screen), +0.3% (grain),
−0.2% (4K, i.e. neutral; an initial −2% reading did not reproduce over
15 interleaved runs). No regression, no missing-kernel red flags large
enough to chase. Counter-based profiling of the AVX-512 paths is not
possible under valgrind (CPUID masking).

## LTO experiment (build configuration, not a code patch)

`-Db_lto=true` on top of the landed patches: instructions/frame a
further −0.2…−0.5%, D1 misses −0.3…−0.9%, and **L1i misses −5…−14%** on
the 1080p corpus, for +37.6 KB .text (+2.1%). Output is bit-exact and
all conformance vectors pass. This generically captures cross-TU
inlining (e.g. `dav1d_prepare_intra_edges`) that source annotations
cannot. Worth recommending to packagers / CI rather than as a source
change; the I-cache result suggests it more than pays for its size on
big-core CPUs, but it should be re-measured on a small-cache ARM device
before being assumed universal.

## Fuzzing guardrail

A libFuzzer build (clang, static lib) seeded with the 22 conformance
vectors ran 58k executions / 15 minutes against the patched tree with
no crashes, hangs, or leaks reported. (The longer-term guardrail
remains dav1d's oss-fuzz coverage.)

## Negative result: cdef_find_dir_c row-window restructure (rejected)

Rewriting the 8-scatter-adds-per-pixel direction search into row-wise
contiguous window adds (intended to enable auto-vectorization) was
**rejected by measurement**: instructions/frame on the pure-C path went
+2.2% (detail-1080p-10bit), +1.3% (grain-10bit), +3.9% (smooth-10bit),
with only -0.2..-0.4% on 8-bit clips. GCC fully unrolls the original
8x8 double loop into constant-offset scalar adds, which the restructure
defeated. Reverted; kept here so the next attempt starts from data.
Similarly, inspection of `prep_8tap_c` (29% of the pure-C path) showed
GCC 13 already vectorizes it and hoists the filter taps; no easy C-level
win there.

## 4K cache-miss attribution

At 4K (30 frames, 1 thread), 99.8% of last-level data read misses and
94.7% of LL write misses are inside the asm DSP kernels (cg_annotate
"???" entries = no-debug-info asm), i.e. inherent pixel traffic: a 4K
sbrow working set simply exceeds cache. There is no C-glue fix; reducing
this means changing tile/sbrow processing granularity, which is
structural future work.
